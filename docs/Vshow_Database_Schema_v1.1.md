# Vshow --- Database Schema & Data Model

**Document status:** Draft v1.0\
**Database:** PostgreSQL (Neon)\
**ORM/migrations:** Drizzle ORM + committed migration files\
**Purpose:** Define the initial relational model and integrity rules for
Vshow Phase 1.

## 1. Design principles

1.  PostgreSQL stores application metadata, workflow state, access
    mappings, audit events, and object-storage references.
2.  Media bytes live in S3-compatible object storage, not in PostgreSQL
    or Vercel function request bodies.
3.  Media versions are immutable. A new upload creates a new version row
    and a new object key.
4.  A review decision refers to the exact version reviewed.
5.  A manager's actual schedule is separate from a convener's requested
    display preference.
6.  VOSS vauth authenticates identity; Vshow owns users, roles,
    committee membership, screen access, and authorization.
7.  Prefer foreign keys, unique constraints, checks, and transactions to
    enforce data integrity.
8.  Use soft deletion/archival where history must be retained; do not
    cascade-delete audit/review history.

## 3. Naming and conventions

-   Table names below are logical names; implementation may use
    snake_case names.
-   Primary keys: UUID, generated by the application or database.
-   Timestamps: `timestamptz`, stored in UTC.
-   Use `created_at` and `updated_at` where applicable.
-   Emails should be normalized (trimmed and lowercased) before
    uniqueness checks.
-   Monetary values are not part of this project model.
-   Do not store raw OAuth access/ID tokens or secrets in these tables.

## 4. Tables

### 4.1 `app_user`

Represents a locally provisioned Vshow user mapped to a verified vauth
identity.

  -----------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- -----------------------
  `id`                    UUID                    PK

  `email`                 `varchar(320)`          Required, normalized,
                                                  unique

  `display_name`          `varchar(200)`          Required

  `vauth_subject`         `varchar(255)`          Optional until reliably
                                                  available; unique when
                                                  present

  `is_active`             boolean                 Required, default
                                                  `true`

  `created_at`            `timestamptz`           Required

  `updated_at`            `timestamptz`           Required
  -----------------------------------------------------------------------

**Rules** - Match authenticated identities by a stable provider subject
where available; normalized verified email can be used as a
bootstrap/mapping attribute, but do not assume email can never change. -
No public self-registration is implied. Provisioning is controlled by
Vshow administrators. - Inactive users must not access the application.

### 4.2 `app_role`

Defines the application roles.

  ------------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- ------------------------
  `id`                    UUID                    PK

  `code`                  enum/text               Unique: `CONVENER`,
                                                  `REVIEWER`,
                                                  `SERVER_ROOM_MANAGER`,
                                                  `ADMIN`

  `name`                  `varchar(100)`          Required

  `description`           text                    Optional

  `created_at`            `timestamptz`           Required
  ------------------------------------------------------------------------

Use a database enum or checked text column. A role lookup table is more
extensible and makes role management easier to evolve.

### 4.3 `user_role`

Allows multiple roles per user and keeps authorization assignments
explicit.

  Column                  Type            Rules / meaning
  ----------------------- --------------- -----------------------------
  `user_id`               UUID            PK part, FK → `app_user.id`
  `role_id`               UUID            PK part, FK → `app_role.id`
  `assigned_by_user_id`   UUID            Nullable FK → `app_user.id`
  `created_at`            `timestamptz`   Required

**Constraint:** unique/primary key `(user_id, role_id)`.

### 4.4 `committee`

  Column          Type             Rules / meaning
  --------------- ---------------- --------------------------
  `id`            UUID             PK
  `name`          `varchar(200)`   Required
  `code`          `varchar(80)`    Required, unique
  `description`   text             Optional
  `is_active`     boolean          Required, default `true`
  `created_at`    `timestamptz`    Required
  `updated_at`    `timestamptz`    Required

### 4.5 `committee_membership`

Maps users to committees and captures committee-specific authority.

  -----------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- -----------------------
  `id`                    UUID                    PK

  `committee_id`          UUID                    FK → `committee.id`

  `user_id`               UUID                    FK → `app_user.id`

  `membership_type`       enum/text               `CONVENER`, `MEMBER`
                                                  (extend only if needed)

  `is_active`             boolean                 Required, default
                                                  `true`

  `assigned_by_user_id`   UUID                    Nullable FK →
                                                  `app_user.id`

  `created_at`            `timestamptz`           Required
  -----------------------------------------------------------------------

**Constraints** - Unique `(committee_id, user_id)`. - Only active
memberships authorize committee-scoped actions. - A user with the global
`CONVENER` role still needs active membership in the committee for that
submission.

### 4.6 `screen`

  Column                   Type                    Rules / meaning
  ------------------------ ----------------------- -----------------------
  `id`                     UUID                    PK

  `name`                   `varchar(200)`          Required

  `code`                   `varchar(80)`           Required, unique

  `location_description`   text                    Optional

  `is_active`              boolean                 Required, default
                                                   `true`

  `external_player_ref`    `varchar(255)`          Optional integration

  `updated_at`             `timestamptz`           Required
  ------------------------------------------------------------------------

Phase 1 does not require the external player reference.

### 4.7 `submission`

One workflow request submitted by a committee convener. Each submission represents exactly one logical media asset, which may have multiple immutable versions.

  -----------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- -----------------------
  `id`                    UUID                    PK

  `reference_code`        `varchar(40)`           Required, unique
                                                  human-readable
                                                  reference

  `committee_id`          UUID                    Required FK →
                                                  `committee.id`

  `created_by_user_id`    UUID                    Required FK →
                                                  `app_user.id`

  `title`                 `varchar(200)`          Required

  `description`           text                    Optional

  `workflow_status`       enum/text               Required; see status
                                                  values below

  `current_version_id`    UUID                    Nullable FK →
                                                  `media_version.id`; set
                                                  after first upload

  `submitted_at`          `timestamptz`           Nullable until first
                                                  submission

  `closed_at`             `timestamptz`           Nullable

  `created_at`            `timestamptz`           Required

  `updated_at`            `timestamptz`           Required
  -----------------------------------------------------------------------

Suggested `workflow_status` values: - `DRAFT` - `PENDING_REVIEW` -
`CHANGES_REQUESTED` - `APPROVED` - `REJECTED` - `CANCELLED`

**Rules** - `current_version_id` must refer to a version belonging to
this submission. PostgreSQL cannot enforce this with a simple FK alone;
validate transactionally or use a composite FK design. - On a new
version, set status to `PENDING_REVIEW` after the convener submits it;
it must not remain manager-eligible based on a previous approval. - A
submission's current version and its latest review state must be updated
atomically.

### 4.8 `media_version`

Immutable record of one uploaded media version.

  -----------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- -----------------------
  `id`                    UUID                    PK

  `submission_id`         UUID                    Required FK →
                                                  `submission.id`

  `version_number`        integer                 Required, starts at 1

  `object_key`            `varchar(1024)`         Required, unique
                                                  storage key; never a
                                                  public permanent URL

  `original_filename`     `varchar(255)`          Required, sanitized for
                                                  display

  `content_type`          `varchar(150)`          Required,
                                                  server-validated

  `size_bytes`            bigint                  Required, greater than
                                                  0

  `checksum_sha256`       `varchar(64)`           Optional but
                                                  recommended

  `uploaded_by_user_id`   UUID                    Required FK →
                                                  `app_user.id`

  `uploaded_at`           `timestamptz`           Required

  `change_note`           text                    Optional
  -----------------------------------------------------------------------

**Constraints** - Unique `(submission_id, version_number)`. - Unique
`object_key`. - `size_bytes > 0`. - Never overwrite an existing
version's object or metadata as a way to update media. - A storage
object should not be deleted while it is referenced by a review or
schedule history record unless an explicit retention/deletion policy
allows it.

**Version workflow** 1. Upload to a new, scoped object key. 2. Verify
upload completion and metadata/checksum server-side where supported. 3.
Insert the version record. 4. Update `submission.current_version_id`. 5.
Invalidate the submission's prior approval for current workflow purposes
and require re-review. 6. Commit the state change atomically; handle
failed uploads/orphan objects with cleanup.

### 4.9 `screen_request`

A convener's requested screen and preferred display window. This is not
the actual schedule.

  -----------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- -----------------------
  `id`                    UUID                    PK

  `submission_id`         UUID                    Required FK →
                                                  `submission.id`

  `screen_id`             UUID                    Required FK →
                                                  `screen.id`

  `preferred_start_at`    `timestamptz`           Optional; null means no
                                                  specific start
                                                  requested

  `preferred_end_at`      `timestamptz`           Optional; null means no
                                                  specific end requested

  `request_note`          text                    Optional

  `created_at`            `timestamptz`           Required

  `updated_at`            `timestamptz`           Required
  -----------------------------------------------------------------------

**Constraints / decisions** - If both times are present, require
`preferred_end_at > preferred_start_at`. - Allow multiple rows per
submission to request multiple screens. - Initial proposal: one active
request row per `(submission_id, screen_id)`; if different windows on
the same screen are required, allow multiple rows and add an explicit
slot/sequence identifier. Confirm this before implementation. - Preserve
the original request when the manager schedules a different time; record
the actual schedule separately. - If request details change after
approval, treat that as an approval-relevant change and send the
submission through review again, unless product policy explicitly says
otherwise.

### 4.10 `review_decision`

Append-only history of each reviewer decision, tied to the exact version
reviewed.

  -----------------------------------------------------------------------
  Column                  Type                    Rules / meaning
  ----------------------- ----------------------- -----------------------
  `id`                    UUID                    PK

  `submission_id`         UUID                    Required FK →
                                                  `submission.id`

  `media_version_id`      UUID                    Required FK →
                                                  `media_version.id`

  `reviewer_user_id`      UUID                    Required FK →
                                                  `app_user.id`

  `decision`              enum/text               `APPROVED`, `REJECTED`,
                                                  `CHANGES_REQUESTED`

  `comment`               text                    Required for
                                                  `CHANGES_REQUESTED`;
                                                  policy may also require
                                                  it for rejection

  `created_at`            `timestamptz`           Required
  -----------------------------------------------------------------------

**Rules** - Decisions are append-only; corrections should be represented
by another record or an explicit audited administrative correction. -
Only an authenticated user with the Vshow `REVIEWER` role may create a decision. Phase 1 reviewer scope is global: any authorized reviewer may review any submission. - The reviewed
version must belong to the same submission. - A decision is current only
if it refers to `submission.current_version_id` and is the latest
applicable decision. Manager eligibility must be derived/validated from
the current version and current approval, not from a stale submission
status alone. - Create decision and update submission workflow status in
one transaction.

### 4.11 `schedule_entry`

A manager-recorded schedule/handoff record. It is separate from the
convener's requested window.

  -------------------------------------------------------------------------
  Column                    Type                    Rules / meaning
  ------------------------- ----------------------- -----------------------
  `id`                      UUID                    PK

  `submission_id`           UUID                    Required FK →
                                                    `submission.id`

  `media_version_id`        UUID                    Required FK →
                                                    `media_version.id`

  `screen_id`               UUID                    Required FK →
                                                    `screen.id`

  `status`                  enum/text               `NOT_SCHEDULED`,
                                                    `SCHEDULED`,
                                                    `PLAYING_CONFIRMED`,
                                                    `COMPLETED`,
                                                    `CANCELLED`

  `actual_start_at`         `timestamptz`           Nullable

  `actual_end_at`           `timestamptz`           Nullable

  `external_schedule_ref`   `varchar(255)`          Optional identifier
                                                    from signage software

  `manager_note`            text                    Optional

  `created_by_user_id`      UUID                    Required FK →
                                                    `app_user.id`

  `updated_by_user_id`      UUID                    Required FK →
                                                    `app_user.id`

  `created_at`              `timestamptz`           Required

  `updated_at`              `timestamptz`           Required
  -------------------------------------------------------------------------

**Rules** - A schedule entry may be created only for the currently
approved version. - The manager must not schedule a stale version if the
submission has a newer current version. - If a version changes after a
schedule has been recorded, mark affected future schedule entries as
needing review/cancellation in an explicit transaction; do not silently
keep them valid. - `PLAYING_CONFIRMED` is a manual claim in Phase 1, not
telemetry from a player. - If repeat slots/recurrence are required,
represent each actual occurrence as a separate row rather than
overloading one row.

-   `app_user.vauth_subject` unique where non-null.
-   `app_role.code` unique.
-   `committee.code` unique.
-   `screen.code` unique.
-   `submission.reference_code` unique.
-   `user_role(user_id, role_id)` primary key.
-   `committee_membership(committee_id, user_id)` unique.
-   `media_version(submission_id, version_number)` unique.
-   `media_version.object_key` unique.
-   `screen_request` time check: end later than start when both are

-   `submission(committee_id, created_at DESC)` for committee

    submissions.
-   `media_version(submission_id, version_number DESC)`.
-   `review_decision(submission_id, created_at DESC)`.
-   `review_decision(media_version_id, created_at DESC)`.
-   `screen_request(screen_id, preferred_start_at, preferred_end_at)`.

## 6. Authorization rules that depend on the schema

Database relationships support authorization, but application code must
enforce it on every server-side operation.

-   **Convener:** requires active user, `CONVENER` role, and active
    membership in the submission's committee.
-   **Reviewer:** requires active user and `REVIEWER` role plus any
    configured review-scope rule.
-   **Server Room Manager:** requires active user and
    `SERVER_ROOM_MANAGER` role.
-   **Administrator:** requires active user and `ADMIN` role.
-   No role in vauth claims should be trusted as the Vshow role
    assignment.
-   Avoid fetching a resource by ID and returning it before checking the
    caller's permissions.

## 7. State transition and transaction rules

### Submit for review

-   Validate the current version exists and belongs to the submission.
-   Validate requested screens and times.
-   Set workflow status to `PENDING_REVIEW`, set `submitted_at`, and
    create an audit event in one transaction.

### Review decision

-   Lock or otherwise protect the submission row against concurrent
    changes.
-   Confirm the reviewed version is still the current version.
-   Insert the review decision.
-   Update workflow status to match the decision.
-   Add audit event in the same transaction.

### New media version

-   Authorize the uploader.
-   Create a unique object key and upload the file.
-   Confirm upload integrity.
-   Insert the immutable `media_version`, update `current_version_id`,
    and set workflow status to `DRAFT` or `PENDING_REVIEW` depending on
    whether the convener explicitly resubmits.
-   Ensure prior approval no longer qualifies the submission for manager
    handoff.
-   Record audit event.
-   Avoid a race in which a reviewer approves the old version after a
    newer version becomes current.

### Manager scheduling

-   Confirm the submission is approved for its current version at the
    moment the schedule is created/updated.
-   Store the exact `media_version_id` scheduled.
-   Store actual schedule details separately from preferred request
    details.
-   Record schedule and audit changes transactionally.

## 8. Drizzle implementation notes

-   Define relations in Drizzle for navigation, but do not rely on ORM
    relations alone to enforce integrity.
-   Use SQL foreign keys and check/unique constraints in migrations.
-   Use PostgreSQL enums or checked text columns consistently. Prefer
    checked text or enums based on the project's migration conventions;
    avoid duplicating a status as unrelated enums without clear reason.
-   Consider a composite FK or transaction-level validation to ensure
    `submission.current_version_id` belongs to the same submission.
-   Generate migrations from schema changes, review the SQL, and commit
    them. Run migrations explicitly in setup/deployment.
-   Never use a destructive schema push/reset against an unknown or
    remote database.

## 9. Confirmed schema decisions

1. **One media asset per submission:** `submission` represents one logical media asset; `media_version` stores its immutable versions.
2. **Multiple requested windows:** `screen_request` allows multiple rows per submission and multiple rows for the same screen, identified by `slot_number`.
3. **Global reviewer scope:** any active user with the `REVIEWER` role can review any submission in Phase 1.
4. **Manual playing status:** `PLAYING_CONFIRMED` is supported in Phase 1 and is a manually entered status, not player telemetry.
5. **Reapproval on approval-relevant changes:** media replacement and changes to title, description, requested screens, or requested windows invalidate prior approval. Use `approval_revision` or an immutable snapshot so approval is tied to the exact reviewed state.
6. **Retain history:** preserve old media versions and review/audit records; retention duration and exceptional deletion rules remain to be decided.

## 10. Remaining decisions before migrations

1. **Admin role assignment:** whether administrators may also hold operational roles.
2. **Actual scheduling recurrence:** whether recurring schedule entries are needed beyond multiple separate entries per submission/screen.
3. **Retention policy details:** retain old versions and review/audit history by default; define duration and any deletion/privacy exceptions before production.
4. **Storage provider:** confirm provider, bucket, key conventions, signed upload/download flow, and maximum file size.
5. **Identity mapping:** confirm the stable subject claim available from vauth and the local-user provisioning process.
6. **Deployment suitability:** verify Vercel plan terms, function limits, and institutional-use suitability.
7. **Approval-relevant metadata history:** choose between a revision/snapshot table or the `approval_revision` approach described above. Either must guarantee that title, description, requested screens, and requested windows changes invalidate prior approval and remain auditable.
8. **Actual schedule multiplicity:** confirm whether each screen may have multiple separate actual schedule entries for one submission; the proposed schema permits it.

## 12. Phase 1 implementation amendments (recorded after approval)

These additions were approved when Phase 1 implementation started (migration `0004_core_workflow`). Nothing above was rewritten; where an item refines an earlier rule, it says so.

1. **`submission_revision`** (new, immutable, append-only): `id`, `submission_id`, `revision_number` (unique per submission), `title`, `description`, `media_version_id` (composite FK proving it belongs to the submission), `requested_windows` (JSONB array of `{screenId, slotNumber, startAt, endAt, note}`), `created_by_user_id`, `created_at`. This is the immutable-snapshot option chosen for §9.5/§10.7. `submission.current_revision_id` points at the current revision (composite FK).
2. **`review_decision.revision_id`** (new, NOT NULL): the exact revision evaluated; composite FKs force it to belong to the submission and to name the same media version as the decision. A trigger accepts a decision only on a `PENDING_REVIEW` submission, for its current revision, by someone other than `created_by_user_id`. Refines §4.10.
3. **Comments:** a rejection reason and a change-request comment are both mandatory (constraint `review_decision_reason_required`; previously only `CHANGES_REQUESTED`).
4. **`submission.resubmission_of_id`** (new, nullable self-reference): a rejected submission is terminal; a resubmission is a new submission linked to it, with its own media and no inherited approval.
5. **`upload_reservation`** (new): one row per server-authorised upload (`id` becomes the media version id, staging and final object keys, declared type and size, status `PENDING|FINALIZED|REJECTED|EXPIRED`). A finished reservation can never change.
6. **`media_version.storage_etag`** (new, nullable): the provider ETag of the validated final object.
7. **`reference_counter`** and `vshow_next_reference_code(year)`: concurrency-safe `VS-YYYY-NNNNNN` codes (year in `Asia/Kolkata`), gap-free per year.
8. **Append-only enforcement** by triggers (UPDATE/DELETE refused) on `media_version`, `review_decision`, `audit_event` and `submission_revision`. TRUNCATE is not blocked by a trigger (the migration safety check forbids that statement in migration files); the application never issues it.
9. **Requested windows (refines §4.9):** both `preferred_start_at` and `preferred_end_at` are required to **submit** (columns stay nullable so an incomplete draft can exist; the service validates), the end must be after the start, the start must be in the future at submission (`Asia/Kolkata`), at most 10 windows by default (`MAX_REQUEST_WINDOWS`), and **overlapping windows are allowed**, including on the same screen at the same time. `slot_number` is assigned per screen by the server.
10. **Reviewers** cannot see drafts and cannot decide on a submission they created. A pending submission cannot be edited; withdrawal is out of scope. Editing or replacing media of an approved submission returns it to `DRAFT` (approval withdrawn, audited as `APPROVAL_INVALIDATED`).
